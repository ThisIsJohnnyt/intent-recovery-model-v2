# PDR-009: Replace Antigravity with a direct Gemini CLI call as the review bridge's transport

**Date**: 2026-09-08
**Status**: Accepted

## Decision

`review_bridge/`'s transport moves from a standing Antigravity session to a
direct, non-interactive Gemini CLI call, invoked by `training/gemini_bridge.py`.
The bridge's own shape is unchanged — `ClaudeProposal.md` in,
`GeminiReview.md` out, both gitignored, overwritten each cycle, alignment
required before implementation, 5-iteration disagreement escalates to the
product owner (see the project's standing `gemini-review-bridge-process`
convention and [PDR-006](PDR-006.md)/[PDR-008](PDR-008.md)). Only the
transport changes.

Default model is `gemini-3.5-flash-lite`; upgrading to `gemini-3.1-pro-preview`
for a specific round requires the same explicit, in-the-moment product-owner
authorization [PDR-004](PDR-004.md) already established for above-routine
Gemini spend — not a default either AI can flip alone.

## Reasoning

### Why change

The product owner exhausted his Antigravity usage under his Google AI
subscription, and Antigravity's actual token draw was heavier than it
appeared — not sustainable as this bridge's standing transport. Antigravity's
role here was never to write code; it only ever read what was given to it,
thought, and replied. A direct, non-interactive Gemini CLI call does exactly
that, at a fraction of the resource cost, billed per-token against the
product owner's own API key instead of subscription usage.

### What was verified live, not assumed, before adopting this

- `@google/gemini-cli` (npm) installs and runs standalone. **This corrects
  [PDR-004](PDR-004.md)'s table**, which stated Google retired the
  standalone Gemini CLI in favor of Antigravity CLI (checked 2026-08-19)
  — that finding was accurate for the tool `jamubc/gemini-mcp-tool` wrapped
  at the time, but does not describe the current state of the official
  `@google/gemini-cli` package itself, which installed clean and ran
  independent of Antigravity when tested 2026-09-08 (version `0.58.0`).
- `gemini -p "<short instruction>" --skip-trust --approval-mode plan
  --output-format json -m <model>`, with the actual prompt content piped via
  stdin (not passed as a command-line argument — see "Windows-specific
  finding" below), runs fully non-interactive and authenticates via the
  `GEMINI_API_KEY` environment variable already configured on this machine,
  no OAuth prompt.
- `--approval-mode plan` is genuinely read-only, enforced by the CLI itself:
  edit and shell tools are unavailable to the model in this mode, not just
  disallowed by convention.
- It reads real files from the workspace on its own initiative when asked
  to (tested against `training/third_party_review.py`) and produced an
  accurate summary.
- `--output-format json` returns exact input/output token counts per call.
  The existing Gemini MCP path (used for corpus batch generation) has never
  returned this — every row in `COST_LEDGER.md`'s batch-generation table
  reads "Not retrieved." This closes that gap for bridge calls going
  forward (see `COST_LEDGER.md`'s new "Gemini CLI (review bridge)" section).

### Windows-specific finding: pipe large content via stdin, not argv

The first real attempt to send a multi-paragraph `ClaudeProposal.md` through
argv (`-p "<the whole proposal>"`, invoked via `cmd /c gemini.cmd ...` since
Windows requires a `.cmd` shim to be run through `cmd.exe`) failed —
`cmd.exe`'s command-line parsing does not handle a large, multi-line string
argument reliably, and it silently dropped `--skip-trust` from what actually
reached `gemini`, reproducing the "untrusted directory" error even though
the flag was present in the Python-side argument list. Fix: keep the `-p`
instruction short (a static, fixed-format request that always fits safely in
argv) and pipe the actual proposal content via stdin instead — which the CLI
explicitly supports (`-p`'s own `--help` text: "Appended to input on stdin
(if any)"). `training/gemini_bridge.py` does this by construction; anyone
extending this script should keep large, variable-length content on stdin,
never in argv, on Windows.

### Cost

`gemini-3.1-pro-preview` (the model this bridge and corpus-generation batches
have used to date) prices at $2.00/$12.00 per million input/output tokens.
`gemini-3.5-flash-lite` prices at $0.15/$1.25 — roughly 10-13x cheaper. The
product owner chose Flash-Lite as the default directly ("default to cheap,
upgrade only when needed"), after seeing real comparative numbers: an
identical trivial call cost $0.017 on Pro vs. $0.0016 on Flash-Lite; a real
file-read-and-summarize call cost roughly $0.03-0.05 on Pro vs. $0.0037 on
Flash-Lite, with no loss of accuracy on that test. A full review-bridge round
(this proposal itself, ~25K input tokens) cost $0.0042 on Flash-Lite. At
these prices, dozens of rounds a day would run pennies to a few dollars a
month — immaterial next to the sustainability problem this PDR solves,
though the model-upgrade-requires-authorization rule stays in place for
rounds that might actually need Pro's deeper reasoning (e.g. adversarial
re-review, a materially different and heavier job than routine proposal
review).

### Trust boundary — raised and addressed during this PDR's own bridge round

Under the prior mechanics, a script *outside* Claude Code handled the
copy/paste both directions, so Claude never controlled what appeared in
`GeminiReview.md`. Under this transport, Claude Code (via
`training/gemini_bridge.py`) is the one invoking the CLI call — meaning
Claude now has the *technical* ability to control both sides of the
exchange, even though the bytes written are always Gemini's real, unedited
API output.

Raised directly to Gemini in the proposal for this PDR, and its own
response (2026-09-08, `gemini-3.5-flash-lite`, full text in that round's
`GeminiReview.md` history): *"sufficiently mitigated by the operational
setup: the product owner tails the live transcript log
(`Get-Content -Wait`), the CLI is invoked with `--approval-mode plan`
(preventing unauthorized edits), and the exact token counts and JSON
outputs can be independently audited against `COST_LEDGER.md`,"* with one
condition attached: `GeminiReview.md` must be Gemini's stdout **verbatim**,
with no pre- or post-processing by Claude Code. `gemini_bridge.py` enforces
this by construction — the reply string from the CLI's own JSON output is
written directly to the file, unmodified.

### Live visibility

The product owner's stated reason for preferring Antigravity originally was
being able to watch the Claude<->Gemini exchange happen, not just read a
final artifact. `training/gemini_bridge.py` preserves this: every call
appends prompt-sent / reply-received / exact usage to
`review_bridge/transcript.log` (append-only, never truncated, so a live tail
survives across multiple rounds), which the product owner watches via
`Get-Content -Wait` in a split VS Code terminal.

## Scope

- Applies only to `review_bridge/`'s transport (engineering/pipeline
  proposal review, model-diagnostics discussion, and this bridge's role in
  periodic adversarial re-review per `PDR-006`). Does not change corpus
  batch generation, which stays on the existing Gemini MCP path
  (`rlabs-inc/gemini-mcp`, `PDR-004`) — that path has its own reasons
  (37+ tool surface, no reported Windows argv issues since Claude invokes
  it via MCP's own protocol rather than a subprocess through `cmd.exe`) and
  isn't part of what's changing here.
- Does not change `training/third_party_review.py` (a fresh, one-shot,
  zero-context Claude API check, deliberately not this bridge — `PDR-008`).
- Revisit if `@google/gemini-cli`'s maintenance status changes materially,
  if Flash-Lite's accuracy proves insufficient for a class of bridge round
  it's actually used for, or if the product owner's Antigravity usage
  situation changes and he wants to reconsider.
