# PDR-016: Route all Gemini connections through FARTS as the Gemini MCP server

**Date**: 2026-09-13
**Status**: Accepted

## Decision

Both remaining direct-to-Google Gemini connections in this repo are replaced
by calls through `C:\Claude Projects\JARVIS FORK` ("FARTS", the product
owner's separate PyQt6 assistant project), which already had its own
working Gemini wiring (API key, `google-genai` client, file-type handlers)
before this change:

- **`.mcp.json`**'s `"gemini"` entry no longer runs `npx -y
  @rlabs-inc/gemini-mcp`. It now runs `python "C:/Claude Projects/JARVIS
  FORK/mcp_server.py"` — a new, headless MCP stdio server added to the
  FARTS repo that does not launch FARTS's GUI, wake-word, mic, or dashboard,
  only its Gemini plumbing (`core/gemini_client.py`,
  `actions/file_processor.py`'s type handlers). It exposes `gemini_query`,
  `gemini_analyze_file`, `gemini_review`, `gemini_speak`, and
  `gemini_read_clipboard`.
- **`training/gemini_bridge.py`** (the standing Claude↔Gemini adversarial
  review bridge transport, see [PDR-006](PDR-006.md)/[PDR-008](PDR-008.md)/
  [PDR-009](PDR-009.md)) no longer shells out to the `gemini` CLI. It opens
  a stdio MCP client connection to the same `mcp_server.py` and calls its
  `gemini_review` tool. The bridge's shape, guardrails, and file layout are
  otherwise unchanged: `ClaudeProposal.md` in, `GeminiReview.md` out
  (verbatim), `transcript.log` appended, `COST_LEDGER.md` logged.

`training/blind_rereviewer.py` (PDR-006's periodic adversarial re-review,
deliberately isolated on its own Windows Credential Manager entry rather
than the shared `GEMINI_API_KEY`) is **not** changed by this PDR — see
Scope below.

## Reasoning

### Why change

The product owner maintains FARTS as a separate, actively-developed
personal-assistant project that already has a Gemini API key configured, a
working `google-genai` client, and a full set of file-type handlers
(images, PDFs, docx, csv/xlsx, json, code, audio, video, pptx). Keeping this
repo's Gemini connections on a third-party npm MCP package
(`@rlabs-inc/gemini-mcp`) and a CLI subprocess (`@google/gemini-cli`)
duplicated that wiring for no benefit, when FARTS's own client code could
be exposed as an MCP server directly — one Gemini connection to maintain
instead of three, and it comes with FARTS's file-processing tools and
TTS/clipboard side effects for free.

### Guardrails preserved, differently enforced

The review bridge's core guarantee — Gemini can read and reply but never
act — no longer comes from the CLI's `--approval-mode plan` flag. Instead,
`mcp_server.py`'s `gemini_review` tool calls `google-genai`'s
`generate_content` with no tools/function-calling attached, so Gemini has
no mechanism to invoke a file or shell action even in principle. The
verbatim-write condition Gemini itself set when PDR-009 was adopted is
unchanged: `gemini_bridge.py` still writes the tool's `reply` string to
`GeminiReview.md` byte-for-byte, no summarizing or editing.

### Live visibility

`gemini_bridge.py` still writes prompt-sent / reply-received / exact usage
to `review_bridge/transcript.log` on every call, so `training/watch_bridge.ps1`
keeps working unchanged — the product owner can still tail the exchange
live regardless of transport.

### Cost tracking

`mcp_server.py`'s `gemini_review` tool returns `usage_metadata`-derived
input/output token counts in its result, same as the CLI's
`--output-format json` did, so `gemini_bridge.py`'s existing
`append_cost_ledger_row` logic needed no changes.

### Trust boundary

Same as PDR-009 established: Claude Code is the one invoking the call
(via `gemini_bridge.py`), so it retains the technical ability to control
both sides, mitigated the same way — live transcript tailing, no
tool-calling attached to the Gemini call, and independent audit against
`COST_LEDGER.md`.

## Scope

- Applies to `.mcp.json`'s `gemini` entry (corpus/dataset generation,
  [PDR-004](PDR-004.md)) and `training/gemini_bridge.py`'s transport
  (review bridge, PDR-006/008/009).
- Does **not** change `training/blind_rereviewer.py`. Its isolation design
  (a separate Windows Credential Manager entry, `"Intent-Recovery-V2"` /
  `"Gemini"`, rather than the shared `GEMINI_API_KEY`) exists specifically
  so its periodic adversarial re-review stays independent of the main
  bridge's plumbing (PDR-006). Routing it through the same FARTS process
  as everything else would undermine that independence, so it keeps calling
  `google-genai` directly with its own credential.
- Does not change `training/third_party_review.py` (a fresh, one-shot,
  zero-context Claude API check — unrelated to Gemini, PDR-008).
- Revisit if FARTS's `mcp_server.py` becomes unmaintained, if running a
  second Python process per call proves too slow for interactive use, or if
  FARTS's own Gemini wiring changes in a way that breaks this repo's usage.

## Correction and follow-up, 2026-09-14: `gemini_bridge.py`'s own call path was never the live one — retired outright

This PDR's original Decision section described `training/gemini_bridge.py`
opening its own stdio MCP connection to `mcp_server.py` and receiving
Gemini's reply back programmatically, within the same call Claude makes.
That is not, and was never, the actual operational flow the product owner
uses. Clarified directly, 2026-09-14: the real mechanism is a **separate**
file-watcher living in the FARTS project itself (outside this repo),
independent of `gemini_bridge.py` entirely — it notices a change to
`review_bridge/ClaudeProposal.md`, forwards it to Gemini, and surfaces the
reply to the product owner through FARTS's own console and text-to-speech.
The product owner then manually copies that reply back into the
conversation with Claude. Claude's role is only to write the proposal file
and stop — never to call `gemini_bridge.py` or any `mcp__gemini__*` tool
directly for this purpose. The one remaining direct Gemini call Claude
makes at all is dataset generation (PDR-004), unrelated to the review
bridge.

Given that, `training/gemini_bridge.py` (unused under the actual flow) and
`training/watch_bridge.ps1` (existed solely to tail a transcript log only
`gemini_bridge.py` ever wrote) are both **removed outright**, not merely
superseded in place. The `mcp>=1.2,<2` pin in `training/requirements.txt`,
added for `gemini_bridge.py`'s own stdio MCP client code, is removed with
it. `.mcp.json`'s `gemini` entry is unaffected and stays — it's shared with
dataset generation, which remains a live, permitted direct call.

Historical references to `gemini_bridge.py` in `PDR-009.md`, `PDR-010.md`,
and `COST_LEDGER.md` are left untouched as the historical record of what
was actually built and used at each point in time, per this project's
append-only convention for accepted PDRs. Two files with comments
comparing their own design against `gemini_bridge.py`'s
(`blind_rereviewer.py`, `generate_blind_rereview_prompt.py`) were updated
to note the retirement rather than reference a file that no longer exists.
