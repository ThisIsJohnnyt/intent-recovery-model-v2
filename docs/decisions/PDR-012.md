# PDR-012: Migrate the base model from flan-t5-base to Qwen3.5-4B

**Date**: 2026-09-09
**Status**: Accepted

## Decision

Migrate the fine-tuning pipeline's base model from `google/flan-t5-base`
(250M params, encoder-decoder, 2022) to `Qwen/Qwen3.5-4B` (4B params,
decoder-only causal LM, 2026, Apache 2.0), trained via 4-bit QLoRA. This is
the project's **first deliberate base-model choice** — verified by reading
the full PDR index — `flan-t5-base` was carried forward from the
predecessor project by default while [PDR-003](PDR-003.md) reset the
corpus; no PDR ever chose it.

## Reasoning

### The evidence: three independent findings all implicate the model, not the corpus

1. **Copying.** `evaluate_real.py`'s last run: mean narrative-vs-input
   similarity **0.76** on the real tier — the model echoes input rather
   than reorganizing it. `check_copy_ratio.py`'s entire apparatus (65
   allowlist entries, six records at ratio exactly 1.000) exists to manage
   this on the corpus side; it has no bearing on inference-time behavior.
2. **The adversarial probe** ([docs/reviews/2026-09-09-adversarial-probe.md](../reviews/2026-09-09-adversarial-probe.md)):
   0 of 12 outputs clean on input mixing recoverable content with
   distressing language; 4 of 12 reached `action_items`.
3. **The HELD learnability test** (experimental, `training/experiments/held_section/`):
   the model learned the output *format* instantly, and got `held` content
   exactly right in all 3 cases it produced any — but showed one
   false-positive duplication and one outright miss on 7 unseen records.
   Format was never the limit; semantic discrimination was.

The corpus itself checked out clean throughout this investigation — 24/24
tests, schema 532/532, copy-ratio breaches nearly all legitimate and
allowlisted rather than defects. A separate direct question the same day
("should Gemini be replaced as the example generator?") was answered no,
based on the HELD batch's 45/45 valid, rule-compliant generation against a
prompt shaped by 9 rounds of adversarial bridge negotiation — nothing in
that result implicates generation quality.

### Hardware: tested empirically on the product owner's actual machine, not estimated

Public sources conflicted on whether 4-bit quantization works on
Windows + Blackwell + CUDA 13.x at all (an open `bitsandbytes` GitHub issue
reports problems on this exact combination). Rather than trust either side,
tested directly on the product owner's RTX 5060 (7.93 GB VRAM, compute
capability 12.0):

| Model | 4-bit load | Forward+backward (project seq length) | Peak VRAM |
|---|---|---|---|
| Qwen2.5-0.5B (smoke test) | ✅ | ✅ (gradients confirmed non-zero) | 0.93 GB |
| **Qwen3.5-4B** | ✅ | ✅ | **4.66 GB / 7.93 GB** |
| Qwen3.5-9B | ✅ | ❌ OOM (fails loading alone, before training) | 7.12 GB to load |

`bitsandbytes==0.50.2` + `peft==0.20.0` confirmed working — the reported
Blackwell issue did not reproduce on this machine. This also overturned a
web-sourced "~6.5 GB for 9B" estimate that did not survive an actual test at
this project's sequence length. **Qwen3.5-4B is the confirmed target; 9B is
confirmed infeasible on this hardware, not merely undesirable.**

### Model facts, verified rather than assumed

- Apache 2.0 (confirmed via `huggingface_hub.model_info` tags) — matches
  `flan-t5-base`'s current terms and [PDR-002](PDR-002.md)'s posture. No new
  licensing question.
- `Qwen/Qwen3.5-4B` is the chat/instruct release (a finetune of
  `Qwen/Qwen3.5-4B-Base`, confirmed via its own tags and a full chat
  template), not the raw pretrained checkpoint.
- **Multimodal** (`image-text-to-text` pipeline tag) — the only 4B chat
  variant Qwen ships; no text-only alternative exists at this size
  (confirmed via `HfApi.list_models`). Never used by this project; the
  measured VRAM figure above already reflects this exact checkpoint's real
  overhead.
- **Thinking mode defaults on.** Confirmed by reading the chat template's
  own jinja logic directly: `enable_thinking=False` must be passed
  explicitly at every generation call, or the template opens an unclosed
  `<think>` block and the model free-generates reasoning before any real
  output.

### Migration scope, reviewed across 4 bridge rounds (~$1.25 total, `gemini-3.1-pro-preview`)

Each round caught a real, independently verified issue before it reached
code:
- `AutoModelForSeq2SeqLM` still present in both eval scripts.
- `ConsecutiveRepeatStop` assumed decoder-only `input_ids` (seq2seq); a
  causal LM feeds the *entire* prompt to stopping criteria from step one,
  risking a false halt on repeated content already present in the user's
  own note.
- That same class was instantiated once *before* the per-record loop; a
  naive per-record `prompt_length` fix would have silently reused record
  #1's value for every subsequent record without also relocating the
  instantiation.
- Raw `tokenizer.decode(out_ids[0])` never sliced off the prompt — for a
  causal LM, `generate()` returns prompt+generation concatenated.
- Both eval scripts still built prompts via raw string concatenation
  instead of the chat template used at training time.
- A tokenization sketch that would have truncated the EOS token off
  over-length training examples by truncating *after* appending it rather
  than before.
- A methodological gap: a strict-JSON parse-failure metric would conflate
  genuine model syntax errors with legitimate early-stop truncations from
  the repeat-guard. Resolved by tracking a `fired` flag on the stopping
  criteria rather than reverting the training-target format.

**Process note, recorded for future bridge rounds:** round 2 of this
proposal was written as a delta on round 1 and lost content when it
overwrote `review_bridge/ClaudeProposal.md` — the bridge is stateless per
round, so Gemini correctly flagged files as "missing" that were genuinely
absent from what it was shown, even though round 1 had covered them.
Rounds 3-4 resent the complete, consolidated scope each time. Future
proposal rounds should default to resending the full cumulative scope, not
a diff, unless a round is trivially small.

## Scope

- **`training/prepare_data.py`**: `MODEL_NAME`; causal-LM tokenization
  (chat-template prompt + target concatenation, `-100`-masked labels over
  the prompt span); `TASK_PREFIX` becomes a system message, not a raw
  prefix; target serialization moves to indented JSON
  (`json.dumps(output, indent=2)`), with the delimited format kept
  available as a measured fallback if genuine syntax-error rate proves
  high; `MAX_INPUT_LENGTH`/`MAX_TARGET_LENGTH` to be re-measured against
  Qwen's tokenizer, not assumed to carry over from T5's.
- **`training/train.py`**: `AutoModelForCausalLM`; `Trainer`/
  `TrainingArguments` (not the `Seq2Seq` variants); `BitsAndBytesConfig` +
  `peft` `LoraConfig` with the exact shapes confirmed working in the
  hardware test (`r=16, lora_alpha=32, lora_dropout=0.05,
  target_modules=['q_proj','v_proj','k_proj','o_proj'],
  task_type='CAUSAL_LM'`).
- **`training/evaluate_real.py` / `training/probe_adversarial.py`**:
  `AutoModelForCausalLM`; prompts built via `apply_chat_template(...,
  enable_thinking=False)` matching training format exactly; decode slices
  off the prompt span; `ConsecutiveRepeatStop` gains `prompt_length`
  (constructed per-record, inside the loop) and a `fired` state flag.
- **`training/requirements.txt`**: `peft>=0.20,<0.21`,
  `bitsandbytes>=0.50,<0.51` — pinned to versions confirmed working on this
  hardware, not a guess.
- **`MODEL_RELEASE_NOTICE.md` / `THIRD_PARTY_NOTICES.md`**: updated to name
  `Qwen/Qwen3.5-4B`, Alibaba/Qwen as upstream author, Apache 2.0 terms, and
  a disclosure that the checkpoint's multimodal capability is present
  upstream but unused by this project.

## Explicitly out of scope

- The `held` output field — still a separate, experimental, undecided
  feature (its own follow-up per that experiment's own design). Not
  bundled into this migration.
- Regenerating `datasets/synthetic.jsonl` — unaffected. Only how
  `prepare_data.py` serializes a record's `output` into the model's
  training target changes; the stored corpus content does not.
- Thought Organizer (the downstream app) — out of scope until this
  checkpoint is validated as an actual improvement over the current one.
