# PDR-010: Genuinely blind periodic re-review via an out-of-repo prompt generator and a stateless CLI auditor

**Date**: 2026-09-08
**Status**: Accepted

## Decision

The Gemini pass of PDR-006's periodic adversarial re-review moves off
`review_bridge/`'s standing transport entirely for this one purpose. Two
new pieces, used together:

- `training/generate_blind_rereview_prompt.py` — reads the corpus, samples
  the due re-review batch per `REVIEW_GUIDE.md`'s existing cadence rule, and
  writes a sanitized rubric (`blind_rereview_rubric_{date}.txt`) and an
  anonymized sample (`blind_rereview_sample_{date}.jsonl`) into
  `review_bridge/` (gitignored). Neither file names this project, any AI
  collaborator, or carries any prior disposition/verdict.
- `training/blind_rereviewer.py` — a standalone script (not part of
  `gemini_bridge.py`) making one stateless `google-genai` `generate_content()`
  call per round: no tools, no function-calling, no chat/session object, so
  the model sees exactly the rubric + sample text and nothing else on this
  machine. Authenticates via Windows Credential Manager (`keyring`, target
  `Intent-Recovery-V2`, username `Gemini`) rather than the `GEMINI_API_KEY`
  env var `gemini_bridge.py`'s CLI transport already uses — a separate,
  occasional-use credential, same reasoning as `PDR-008`'s Claude-key
  handling.

The product owner also has a separate AI Studio app performing the same
two-file audit manually (drag-and-drop + a rubric text box); the CLI script
is the automatable equivalent of the same mechanism, not a competing
design — either can run a given round.

## Reasoning

### Why this, not `gemini_bridge.py`/`review_bridge/`

PDR-006's 2026-09-07 amendment required the Gemini pass run with "no
exposure to the standing bridge's own conversation history," originally via
Antigravity's `invoke_subagent` (a genuinely isolated context window).
PDR-009's CLI replacement has no equivalent: every call is a fresh process
with no memory, but `--approval-mode plan` still grants the model read-only
access to this entire repository — which could let it reconstruct exactly
the prior-round context (`transcript.log`, prior `GeminiReview.md` files,
PDR documents) the isolation design wants kept out. A stateless API call
with zero tools attached closes that gap structurally rather than by
convention: there is no mechanism by which the model could read anything
beyond the two strings in the prompt, regardless of what invokes the call.

### Two decisions reached before building it, not unilaterally

- **No prior disposition/verdict in the sample, anonymized or otherwise.**
  Matches `REVIEW_GUIDE.md`'s existing rule exactly (drafted, then
  confirmed directly with the product owner rather than assumed).
- **Category and difficulty labels ARE included per record.** Tried
  omitting them first; several checklist rules (verbatim-preservation
  scoped to exactly three categories; difficulty-comparison) only apply
  correctly with the category known, and omitting them risked reproducing
  a known failure mode (over-applying verbatim-preservation to
  `self_correction`, which the checklist explicitly excludes). Reviewed via
  `review_bridge/` before implementation (round on "genuinely blind
  re-review prompt generator," 2026-09-08) — Gemini confirmed the
  sanitized checklist lost no rule substance and the sample-selection logic
  didn't leak more than intended.

### What was actually tested, not assumed, before trusting either tool

- **First AI Studio run** (web GUI): returned a fully fabricated audit —
  wrong record count, invented categories foreign to this project
  ("Payment Authorization Security"), fictional content (a Kafka rebalance
  incident, a payment-gateway exploit), rules that don't exist in the
  rubric ("no hyperbolic marketing jargon"). Diagnosed as the app not
  actually passing the synced files to the model for that run; not used.
- **Second AI Studio run**: genuine, `payloadVerification` confirmed real
  record IDs/categories/rubric snippet reached the model. Four FAILED
  verdicts, independently checked against the real corpus content: three
  did not hold up (a sequential-elimination note misread as an unresolved
  contradiction; a hedge word ["Think"] cited as absent when it was
  literally present in the quoted evidence; a self-contradicting rationale
  that admitted compliance with a rule and failed the record anyway). The
  report's own `overallComplianceScore` (25) didn't reconcile with either
  the visible per-record average (70.5) or the pass rate (60%) — an
  unexplained aggregation bug on the app's side, not a corpus finding.
- **First `blind_rereviewer.py` run** (CLI, same 10-record sample): 0/10
  ACCEPT, every record FIX. Checked several cited violations directly
  against the record text: multiple were backwards (a hedge word cited as
  *invented certainty*, the opposite of what hedging is), or factually
  wrong about the field/content being described. Root cause: the script's
  `SYSTEM_INSTRUCTION` (authored by the AI Studio app, not reviewed before
  first use) had no counterweight against inventing findings, unlike
  `gemini_bridge.py`'s own `INSTRUCTION`, which explicitly says a low-effort
  review with no genuine issues found is a failure of the review, not a
  success.
- **Second `blind_rereviewer.py` run**, after adding that counterweight
  (an explicit verify-before-flagging directive with the same worked
  exceptions `REVIEW_GUIDE.md` itself had to learn — a shared-breath causal
  connective isn't invented causality; a carried-through hedge isn't
  invented certainty): 3 ACCEPT / 7 FIX / 0 REJECT on the identical 10
  records. Independently checked every FIX claim: two held up cleanly (an
  invented "Deciding to..." resolving a stated "maybe"; a narrative naming
  "to completely disconnect" as the trip's purpose, an inferred frame the
  input never states), one reconfirmed the already-known, still-open C2
  finding (narrating a self_correction pivot instead of dropping it), one
  was minor but defensible, and two did not hold up — flagged by a direct,
  checkable internal inconsistency: the same run's own ACCEPT verdict on
  record 3 explicitly praised keeping an identical hedge-prefixed action
  item as *compliant*, while records 4 and 7 were FIXed for the same
  pattern.

### What this does and doesn't establish

This is real improvement, verified by direct comparison on the same
records, not asserted. It is not evidence the tool is fully reliable
unsupervised — the second run still needed reconciliation on 2 of 10
records via direct re-check against the corpus, the same amount of
disagreement-resolution every actual Gemini re-review pass in this
project's history has needed. Every future round's findings still get
checked against the real corpus before disposition, per this project's
standing practice — this PDR adopts the mechanism, not a claim that its
output can be trusted at face value.

## Scope

- Applies only to the Gemini pass of PDR-006's periodic adversarial
  re-review. Does not change `review_bridge/`'s engineering-proposal bridge
  (`PDR-009`), corpus batch generation (`PDR-004`), or
  `third_party_review.py` (`PDR-008`) — three separate mechanisms for three
  separate purposes, unchanged.
- Claude's own fresh-subagent second pass (PDR-006) is unchanged.
- The AI Studio app and the CLI script are two front-ends to the same
  mechanism (a stateless, tool-free model call over the same two files);
  either may be used for a given round at the product owner's discretion.
- Revisit if a future round reproduces the 0-ACCEPT pattern despite the
  counterweight instruction (would suggest the fix didn't generalize past
  this one sample), or if `google-genai`'s stateless call behavior changes
  in a way that reintroduces tool access.
