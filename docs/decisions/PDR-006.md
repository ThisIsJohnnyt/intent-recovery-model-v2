# PDR-006: Reviewer-independence analysis and periodic adversarial re-review

**Date**: 2026-08-19
**Status**: Accepted

## Decision

Two things, prompted by the product owner directly asking whether dropping
to a two-AI-model partnership (Claude + Gemini, per [PDR-001](PDR-001.md))
risks a quality loss versus v1's setup:

1. **This PDR records the answer**, since nothing in this repository's
   existing docs (any PDR, `GOLD_PHILOSOPHY.md`, `AI_COLLABORATION.md`)
   discusses reviewer count or justifies why two collaborators are
   sufficient — that was a genuine gap, not a buried answer.
2. **A supplementary safeguard is adopted**: a periodic, fresh-context
   adversarial re-review of already-accepted corpus content, specifically
   to catch the one real risk this analysis surfaced — see "The actual
   risk" below.

## Reasoning

### Why v2's examples are landing cleaner than v1's, per what's actually documented

Two separate things were conflated in the question and are worth
separating:

**The transport-layer change (v1's hand-rolled HTTP + Codex-drafted
tooling vs. v2's MCP server) is real but doesn't explain content quality.**
[PDR-004](PDR-004.md)'s "Guardrail redesign" is explicit that what got
retired was *wire-format correctness verification* (hash-pinning,
`gate5_pre_execution_attestation_template.json`) — catching malformed
requests and broken response parsing, not evaluating example quality. A
maintained MCP server means fewer failed API calls; it says nothing about
whether an example that *did* come back is any good.

**What actually explains it is a visible, working diagnose-and-fix loop**,
documented batch-by-batch in `training/COST_LEDGER.md`:

- Batch 1: 13/15 accepted (2 rejected)
- Batch 2: 14/15 (1 rejected — same failure mode recurring from batch 1)
- Batch 3: 14/15, with a diagnosed pattern — Gemini repeatedly collapsing
  `contradictory_statement`/`dangling_reference` into
  `self_correction`-shaped output when the category was merely *named* in
  the prompt
- Batch 4: 15/15, zero rejections — after that diagnosis was turned into a
  fix (explicit contrastive "what this is NOT" definitions replacing plain
  category names)

That's evidence of a working review-and-correct cycle, not a claim that
v2's first attempt was simply better.

**The one thing the product owner specifically identified as v1's actual
failure — Gemini generating near-duplicates, tripping collision rules
until runs stalled — is directly named and addressed**:
[`TAXONOMY.md`](../datasets/TAXONOMY.md) states this was v1's failure
mode; `training/check_duplicates.py` replaces whatever v1's broken
mechanism was with a transparent, non-blocking lexical similarity check
that surfaces candidates for human judgment instead of halting generation.

### Was reviewer count actually reduced?

No, per what's documented. [PDR-001](PDR-001.md) records that in v1,
Codex's role was co-authoring the *generation tooling itself*
(`training/gemini_generator_gate2/`, "a Codex-drafted, Claude-reviewed
dataset-generation tool") — not reviewing generated *content*. In both v1
and v2, per every doc that describes the review process
(`docs/datasets/REVIEW_GUIDE.md`, `docs/vision/AI_COLLABORATION.md`),
content review has always been: the generating model produces output,
Claude reviews it independently against a checklist, the product owner
holds final authority. That structure is unchanged. A third AI reviewer
of *content* never existed to be removed.

### The actual risk

That said, the question surfaces a real structural risk worth naming
plainly rather than dismissing: **the same collaborator (Claude) writes
the generation prompts and taxonomy definitions, and then reviews the
output against that same understanding.** A systematic blind spot in how
a category is understood would be consistent between prompt-writing and
review — nothing in the current loop would catch it, because it wouldn't
look like a contradiction, it would look like agreement. The batch-to-batch
evidence above shows real, varied defects being caught, which is
reassuring against *known* failure classes, but it isn't evidence against
a defect nobody currently knows to look for.

## What this PDR adopts

**Periodic fresh-context adversarial re-review**: on a defined cadence (see
`docs/datasets/REVIEW_GUIDE.md`'s new "Periodic adversarial re-review"
section for the operational detail), a sample of *already-accepted* corpus
examples is re-reviewed by an agent with no involvement in writing that
batch's generation prompts or taxonomy revisions, instructed to look
adversarially for defects independent of the original review's
conclusions.

**What this does and doesn't solve, stated plainly**: this reduces
same-context correlation bias (the reviewer isn't grading its own
homework, prompt-writing-wise) — it does **not** solve model-family
correlation bias, since the fresh-context reviewer is still Claude, not an
architecturally independent model. If that gap matters more later, the
stronger options considered and not adopted now were: Gemini
self-critiquing its own output (weaker — same model that generated it) and
the product owner doing hand spot-checks directly (strongest, but costs
the product owner's time rather than API budget). Revisit if the current
approach's findings suggest it isn't enough.

## Amendment, 2026-08-25

This PDR's own trigger fired: "revisit if the current approach's findings
suggest it isn't enough." It took four periodic re-reviews (all Claude,
fresh-context) to surface a defect class the first three missed — the
narrative-voice drift documented in `REVIEW_GUIDE.md`'s 2026-08-25 log
entries — and the fresh-context re-review that *did* eventually catch part
of it still left 15 non-first-person narratives and 26 third-person
bullet sets undetected for three weeks, found only by the product owner's
own hand spot check, not by any Claude review pass.

**Calibration, not a full swap.** Rather than adopt the double-review
design PDR-006 originally deferred ("stronger options considered and not
adopted now"), a bounded test was run first: 12 blind examples, half known
defects pulled from this session's own pre-fix git history, half untouched
controls, identical prompt sent independently to Gemini and to a
fresh-context Claude agent, neither shown the other's output. Full detail
in `REVIEW_GUIDE.md`'s adversarial-re-review log, 2026-08-25 entry.

**Result: Gemini caught 5/6 known defects: Claude caught 2/6.** The four
Claude misses were exactly the defect classes — third-person voice,
third-person bullets, non-recovery — this session existed to fix, one of
them matching the checklist's own worked example almost verbatim. This is
model-family correlation bias, the exact gap this PDR named as unsolved by
fresh-context re-review alone, observed directly rather than argued for.

**Adopted, narrowly**: the next periodic re-review (due after batch 12,
already slated to sample examples edited during this session) gives
Gemini first pass on the full `REVIEW_GUIDE.md` 0–8 checklist, with Claude
as the second reviewer per the original design — disagreement is still the
signal, not a ranking. This is **not** a decision to retire Claude from
the review loop, or to make Gemini-first standing policy — one 12-example
run is not enough evidence for that, and this PDR's own history (a
"check by batch first" rule added and then retracted after generalizing
from a single incident) is the argument against over-fitting to it. Treat
the next live re-review's result as the second data point, and revisit
this amendment once it lands.

## Amendment, 2026-09-07

The 2026-08-25 amendment's Gemini-first ordering used a stateless
`gemini-query` (API/MCP) call for the Gemini pass — independent of Claude's
own reasoning by construction (no memory between calls), but not
independent of anything else: it's the same model, prompted directly by
whichever Claude session is running the re-review, every time.

**Two things prompted revisiting this.** First, a new Claude<->Gemini
review bridge (`review_bridge/`, a standing Antigravity session, separate
from the batch-generation API) was introduced this session for
engineering/pipeline proposal review, and the product owner observed that
a persistent, more capable reviewer session might do adversarial re-review
better than a one-shot API call too — which the 13th re-review actually
demonstrated: the API-based Gemini pass over-rejected 4 records on a rule
that, checked directly against `real_validation.jsonl`, would have called
the product owner's own real hand-written note wrong.

Second, routing adversarial re-review through the *same* standing bridge
session risked reintroducing the exact correlation-bias problem this PDR
exists to prevent, just relocated: that session had, within the same
session, already aligned on a batch's design (via the engineering-proposal
bridge) before being asked to adversarially re-review that batch's
resulting content. Asked directly, the Antigravity session confirmed it
has its own subagent tooling (`invoke_subagent`) — a fresh, isolated
context window with no access to the ongoing bridge conversation, seeing
only the explicit prompt passed to it. This is a direct analog to Claude's
own fresh-subagent second pass.

**Adopted**: the Gemini pass of periodic adversarial re-review now runs as
a subagent the Antigravity session spawns fresh for each re-review — given
only `REVIEW_GUIDE.md` items 0-8 and the sampled examples, no exposure to
the standing bridge's engineering-proposal history or that batch's own
design discussion. The standing session relays the subagent's findings
into `GeminiReview.md` without editorializing. Claude's own independent
fresh-subagent pass and the reconciliation step are unchanged. The
batch-generation API call (`gemini-query`) is untouched by this
amendment — it is, and remains, used only for generating new corpus
examples, never for review.

Reached via the review bridge itself (`review_bridge/`, round 1, this
topic), not decided unilaterally by either collaborator.

## Scope

- Supplementary, not a replacement for `REVIEW_GUIDE.md`'s per-batch
  checklist, which still runs on every batch before initial acceptance.
- Applies going forward from this PDR; does not retroactively invalidate
  batches 1–4, which are already documented in `COST_LEDGER.md` and
  `CATEGORY_REFERENCE.md`.
- See `REVIEW_GUIDE.md` for cadence, sample size, and process detail —
  kept there since it's operational, not a decision record.
